# Contract

The one description of Recall's data, scheduling, sync, local protocol and HTTP API. The Rust core, the CLI, the
desktop app, the Worker and the mobile clients all implement this file. Change it in the same commit as the code.

## Data

All IDs are 26-character Crockford base32 ULIDs generated by whoever creates the entity. All times are Unix
milliseconds (`i64` / `number`).

```
Deck   { id, name, parent_id: Id | null, created_at, updated_at, deleted: bool }
Card   { id, deck_id, content: string, tags: string[], created_at, updated_at, deleted: bool }
Review { id, card_id, rating: 1 | 2 | 3 | 4, reviewed_at, duration_ms: number | null }
```

- Ratings: `1` again, `2` hard, `3` good, `4` easy.
- Reviews are immutable and append-only. Decks and cards are soft-deleted (`deleted: true`) so deletes sync.
- `tags` are lowercase, trimmed, deduplicated and sorted; `#` is stripped.

## Card content

A card is Markdown. A line containing only `---` splits it into sides: side 0 is the front, the rest are revealed in
order. Content with no separator is a one-sided note card whose whole text is the front.

```
What is the capital of France?
---
Paris
```

Later: cloze (`{{word}}`), templates, attachments. They aren't part of v1.

## Scheduling

Recall schedules with FSRS-6 using its published default parameters and 90 % desired retention, implemented in
`crates/srs` (no dependencies, deterministic, compiled to wasm for the Worker).

A card's schedule is **derived**: fold its reviews ordered by `(reviewed_at, id)` through the scheduler, starting
from a new card. Two devices that reviewed the same card offline therefore converge after sync. Stores may cache the
result but must recompute it when a review arrives out of order.

```
Schedule { state: "new" | "learning" | "review" | "relearning", due: ms, stability, difficulty, reps, lapses, last_review: ms | null }
```

A new card is due immediately. A card is due when `due <= now`. The review queue is due cards ordered by `due`, then
new cards ordered by `created_at`, capped at 20 new cards per deck per local day (a deck's allowance is 20 minus
the cards in it first reviewed today).

## Sync

Each device keeps its own SQLite store and syncs with one hub: the user's Durable Object on Recall Cloud, or a
self-hosted `recall-hub` reached over Iroh (see Self-hosted hub). Both speak the same request and response and
apply the same rules; only the transport differs.

```
Change = { kind: "deck", value: Deck } | { kind: "card", value: Card } | { kind: "review", value: Review }

POST /v1/sync
  request:  { cursor: number | null, changes: Change[] }
  response: { cursor: number, changes: Change[] }
```

- The server assigns every accepted change a monotonically increasing `seq`. The response holds every stored
  change with `seq > request.cursor` that this request didn't send, and `cursor` is the highest `seq` now stored.
- Decks and cards merge last-writer-wins on `updated_at`; ties keep the stored value. An older incoming write is
  ignored and not echoed back, but a stored value that beat the one a request sent (newer, or a tie with different
  content) is returned to it whatever the cursor. A local
  edit sets `updated_at` to `max(now, previous updated_at + 1)`.
- Reviews merge by union on `id`.
- A client sends everything it changed since its last successful sync, then applies the response with the same merge
  rules, then stores `cursor`. Syncing is idempotent: resending a change is harmless.

## Accounts (interim)

Until real sign-in lands, an account is a secret token.

```
POST /v1/accounts -> { user_id, token }      token = "rc_" + user_id + "_" + 32 random base32 chars
```

The Worker routes a request to the Durable Object named by the token's `user_id`; the DO stores only a SHA-256 hash
of the secret and rejects mismatches with 401. Clients send `Authorization: Bearer <token>`.

## Self-hosted hub

`recall-hub` is a Rust binary that holds one library (any number of devices) and does the Durable Object's job on
hardware the user owns: a NAS, a Pi, a VPS. It's an always-online peer, not a mesh: devices only ever sync with
the hub, so a phone and a sleeping laptop still converge. It reuses `crates/core`'s store and merge, so its sync and
scheduling behave exactly like a device's.

- **Transport.** Iroh, dialled by the hub's endpoint ID, direct where possible and through a relay otherwise, so it
  needs no open ports, DNS or certificates. n0's public relays by default; `recall-hub serve --relay <url>` (and
  `RECALL_RELAY=<url>` for devices) for a self-hosted `iroh-relay`.
- **Sync, ALPN `recall/sync/1`.** One bidirectional stream per sync. Frames are a big-endian `u32` length followed by
  JSON. The device sends the same body as `POST /v1/sync`, the hub answers with the same response, or with
  `{ error: { code, message } }` if the request failed. Frames are at most 128 MiB on `recall/sync/1` and 16 KiB on
  `recall/pair/1` and for events. While a device is connected the hub also opens a unidirectional stream (on the
  first event) and sends `{ "event": "changed", "cursor": n }` frames after any write from another device, so open
  devices pull within a second. A device syncs whenever its connection is (re)established.
- **Devices.** The hub accepts connections only from endpoint IDs in its device list, checked on accept and again
  before each stream; removing a device closes its open connections. Refusals and removals close the connection with
  application code `403`, which a device reports as `unauthorized`; `503` means the hub is busy.
- **Pairing, ALPN `recall/pair/1`.** `recall-hub pair` prints a ticket (`rchub1` + base32 of the hub's endpoint
  address, relay URL and a one-time 128-bit secret) and a QR code, valid for 10 minutes and one use. A device dials
  the hub, sends `{ secret, name }` (`secret` as 32 hex characters, `name` 1 to 64 printable characters), and the
  hub adds the device's endpoint ID and answers `{ library_id }`, or an error with code `bad_ticket`, `ticket_used`
  or `ticket_expired`. The ticket's bytes are the 32-byte endpoint ID, the 16-byte secret, the relay URL (`u8`
  length, then UTF-8; empty for none) and up to 8 direct addresses (`u8` count, then per address `4` or `6`, the IP
  and a big-endian `u16` port); base32 is lowercase RFC 4648 without padding, read case-insensitively. Tickets live
  in the running hub's memory; `recall-hub pair` asks it for one over its control socket (`hub.sock` in the data
  directory, mode `0600`). `recall-hub devices` lists and removes devices. The library id is the hub's store id.
- **Keys.** Each device keeps an Ed25519 secret key in `$RECALL_HOME/iroh.key` (mode `0600`, 64 hex characters);
  it is its endpoint ID. The hub keeps its own under its data directory.
- **Signed in to a hub**, a device's `status.server` is `hub:<endpoint id>` and `status.connected` says whether it
  holds a live connection. Devices dial the relay and direct addresses from the ticket and use n0's relays and
  address lookup unless `RECALL_RELAY=<url>` names a self-hosted relay. `RECALL_NET=local` (hub and devices) means
  loopback only, no relays: for tests and trying it out on one machine.
- **HTTP API and MCP (optional).** `recall-hub --http 127.0.0.1:8787` serves the HTTP API below and `/mcp`, with
  tokens from `recall-hub tokens create`. Put it behind your own proxy or tunnel to reach it remotely.

The HTTP API exists twice, in the Worker (TypeScript) and the hub (Rust). `tests/conformance` is one black-box suite,
run against a base URL, that both must pass; a behaviour isn't in the contract until it's tested there.

## HTTP API

Served by the Worker and by `recall-hub --http`. JSON in and out; errors are `{ error: { code, message } }` with a
matching status, and `code` is one of `invalid_params` (400), `unauthorized` (401), `not_found` (404), `conflict`
(409) or `internal` (500), the same codes the local core uses. Sync rejects a whole request with 400 if any ID isn't
a ULID.

"Today" (the new-card cap, `reviews_today`) is the caller's local day. Devices know it; over HTTP a client sends an
IANA zone in `X-Recall-Timezone`, and a server without one uses UTC. (The Worker uses UTC until it reads the header.)

| Method | Path | Body / query | Returns |
| --- | --- | --- | --- |
| GET | `/health` | | `{ ok: true, version }` (no auth) |
| POST | `/v1/accounts` | | `{ user_id, token }` (no auth) |
| GET | `/v1/decks` | | `{ decks: DeckSummary[] }` |
| POST | `/v1/decks` | `{ name, parent_id? }` | `Deck` |
| PATCH | `/v1/decks/:id` | `{ name?, parent_id? }` | `Deck` |
| DELETE | `/v1/decks/:id` | | `{ ok: true }` (soft-deletes its subdecks and all their cards too) |
| GET | `/v1/cards` | `?deck_id&q&tag&due=true&limit=50&offset` | `{ cards: CardView[] }` |
| POST | `/v1/cards` | `{ deck_id, content, tags? }` or `{ cards: [...] }` | `CardView` or `{ cards: CardView[] }` |
| GET | `/v1/cards/:id` | | `CardView` |
| PATCH | `/v1/cards/:id` | `{ content?, tags?, deck_id? }` | `CardView` |
| DELETE | `/v1/cards/:id` | | `{ ok: true }` |
| GET | `/v1/review/next` | `?deck_id` | `{ card: CardView \| null, remaining: { due, new } }` |
| POST | `/v1/cards/:id/reviews` | `{ rating, duration_ms? }` | `CardView` |
| GET | `/v1/stats` | `?deck_id` | `{ cards, due, new, reviews_today, retention_30d }` |
| POST | `/v1/sync` | see Sync | see Sync |

```
DeckSummary = Deck & { cards: number, due: number, new: number }
CardView    = Card & { sides: string[], schedule: Schedule }
```

`q` matches card content case-insensitively. Deleted entities never appear outside `/v1/sync`. A `deck_id` filter
(cards, review, stats) covers the deck and its subdecks, and a `DeckSummary`'s counts include its subdecks. `due`
counts reviewed cards with `due <= now`; `new` counts new cards available today under the cap; `remaining` includes
the returned card. `retention_30d` is `null` when there is nothing to measure.

## MCP

The Worker and the hub serve MCP over Streamable HTTP at `/mcp` with the same bearer token, and `recall mcp` serves
it over stdio from any device through the local core, so agents work offline and against either backend. Tools
mirror the API:
`list_decks`, `create_deck`, `search_cards`, `create_cards` (batch), `update_card`, `delete_card`, `next_review`,
`review_card`, `stats`. Each tool's description says what a card's `---` separator means, so an agent writes
two-sided cards.

## Local core protocol

On a desktop the `recall core` process owns the store and sync; the CLI and the desktop app are its clients. It
listens on a Unix socket at `$RECALL_HOME/core.sock` (mode `0600`; `RECALL_HOME` defaults to
`~/Library/Application Support/Recall` on macOS and `$XDG_DATA_HOME/recall` elsewhere). Clients start it if it isn't
running.

Each message is one line of JSON. Requests are `{ id, method, params }`; replies are `{ id, result }` or
`{ id, error: { code, message } }`. The core also pushes `{ event: "changed" }` to every open connection after any
write, including writes arriving through sync, so clients refetch.

| Method | Params | Result |
| --- | --- | --- |
| `status` | | `{ version, home, signed_in, last_sync: ms \| null, server: string \| null, sync_error: string \| null, connected: bool \| null }` |
| `decks.list` | | `DeckSummary[]` |
| `decks.create` / `decks.update` / `decks.delete` | as the HTTP bodies, plus `id` for update/delete | as HTTP |
| `cards.list` / `cards.get` / `cards.create` / `cards.update` / `cards.delete` | as HTTP | as HTTP |
| `review.next` | `{ deck_id? }` | as `GET /v1/review/next` |
| `review.answer` | `{ card_id, rating, duration_ms? }` | `CardView` |
| `stats` | `{ deck_id? }` | as HTTP |
| `sync.login` | `{ server, token? }` (creates an account when `token` is omitted), or `{ hub: ticket, name? }` (name defaults to the host name) | `{ user_id, token }` or `{ library_id }` |
| `sync.now` | | `{ pushed, pulled }` |
| `shutdown` | | `{ ok: true }` |

The core syncs on its own after each write (debounced 2 s) and every 60 s while signed in, and with a hub also as
soon as the hub reports a change.
